1. GitHub App Authentication Best Practices

1.1 Authentication Flow Overview

GitHub App authentication follows a two-step token exchange: generate a short-lived JWT from the private key, then exchange it for an installation access token.

Step 1: Generate JWT (max 10-minute TTL)
  ├── Algorithm: RS256
  ├── Claims: iat (issued at, -60s for clock drift), exp (max +10min), iss (App ID or Client ID)
  └── Signed with App PEM private key

Step 2: Exchange JWT for Installation Access Token
  ├── POST /app/installations/{installation_id}/access_tokens
  ├── Auth header: Bearer <JWT>
  └── Returns: ghs_ prefixed token (1-hour TTL)

Step 3: Use installation token for API calls
  ├── Auth header: Bearer ghs_xxxxx...
  └── Automatically expires after 1 hour

1.2 JWT Generation — Python Implementation

import jwt
import time

APP_ID = 123456  # or Client ID string
PRIVATE_KEY_PATH = "./private-key.pem"

with open(PRIVATE_KEY_PATH, "r") as f:
    private_key = f.read()

now = int(time.time())
payload = {
    "iat": now - 60,   # Issued 60 seconds ago (clock drift protection)
    "exp": now + (5 * 60),  # Expires in 5 minutes (max 10)
    "iss": APP_ID       # App ID or Client ID
}

token = jwt.encode(payload, private_key, algorithm="RS256")
print(token)

1.3 JWT Generation — Bash Implementation

#!/bin/bash
APP_ID="123456"
PRIVATE_KEY_PATH="./private-key.pem"

NOW=$(date +%s)
EXPIRY=$((NOW + 300))  # 5 minutes

HEADER=$(echo -n '{"alg":"RS256","typ":"JWT"}' | base64 -w0 | tr '+/' '-_' | tr -d '=')
PAYLOAD=$(echo -n "{\"iat\":${NOW},\"exp\":${EXPIRY},\"iss\":${APP_ID}}" | base64 -w0 | tr '+/' '-_' | tr -d '=')

HEADER_PAYLOAD="${HEADER}.${PAYLOAD}"
SIGNATURE=$(openssl dgst -sha256 -sign "${PRIVATE_KEY_PATH}" <(echo -n "${HEADER_PAYLOAD}") | base64 -w0 | tr '+/' '-_' | tr -d '=')

echo "${HEADER_PAYLOAD}.${SIGNATURE}"

2. Self-Hosted Runner Registration with App Tokens

2.1 Authentication Flow for Runner Registration

1. Generate JWT from PEM private key (RS256, 5-min TTL)
2. Exchange JWT for Installation Access Token (1-hr TTL)
   POST /app/installations/{installation_id}/access_tokens
3. Use Installation Token to get Runner Registration Token
   POST /repos/{owner}/{repo}/actions/runners/registration-token
   OR POST /orgs/{org}/actions/runners/registration-token
4. Use Registration Token with config.sh
   ./config.sh --url <url> --token <registration_token> --unattended
Critical: The config.sh script does NOT know or care whether the registration token came from a PAT or GitHub App. The authentication method choice is entirely upstream — it only affects how you obtain the registration token from the API.

2.2 Registration Token API Endpoints

ScopeEndpointPATFine-Grained PATApp Token
RepositoryPOST /repos/{owner}/{repo}/actions/runners/registration-tokenYesYesYes
OrganizationPOST /orgs/{org}/actions/runners/registration-tokenYesNoYes
EnterprisePOST /enterprises/{ent}/actions/runners/registration-tokenYesNoNo
Limitation: GitHub App authentication is NOT supported for enterprise-level runner registration (documented GitHub limitation). Enterprise runners must use PAT.

2.3 Single Runner Registration — Complete Script

#!/bin/bash
# register_runner_with_app.sh
set -euo pipefail

APP_ID="123456"
INSTALLATION_ID="654321"
PRIVATE_KEY_PATH="./private-key.pem"
OWNER="POWERFULMOVES"
REPO="PMOVES.AI"
RUNNER_NAME="spark-app-auth"
RUNNER_LABELS="self-hosted,spark,Linux,ARM64"

# Step 1: Generate JWT
NOW=$(date +%s)
EXPIRY=$((NOW + 300))
HEADER=$(echo -n '{"alg":"RS256","typ":"JWT"}' | base64 -w0 | tr '+/' '-_' | tr -d '=')
PAYLOAD=$(echo -n "{\"iat\":${NOW},\"exp\":${EXPIRY},\"iss\":${APP_ID}}" | base64 -w0 | tr '+/' '-_' | tr -d '=')
HEADER_PAYLOAD="${HEADER}.${PAYLOAD}"
SIGNATURE=$(openssl dgst -sha256 -sign "${PRIVATE_KEY_PATH}" <(echo -n "${HEADER_PAYLOAD}") | base64 -w0 | tr '+/' '-_' | tr -d '=')
JWT="${HEADER_PAYLOAD}.${SIGNATURE}"

# Step 2: Get Installation Access Token
INSTALL_TOKEN=$(curl -s -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer ${JWT}" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  "https://api.github.com/app/installations/${INSTALLATION_ID}/access_tokens" | jq -r '.token')

# Step 3: Get Runner Registration Token
REG_TOKEN=$(curl -s -X POST \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer ${INSTALL_TOKEN}" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  "https://api.github.com/repos/${OWNER}/${REPO}/actions/runners/registration-token" | jq -r '.token')

# Step 4: Configure runner
./config.sh \
  --url "https://github.com/${OWNER}/${REPO}" \
  --token "${REG_TOKEN}" \
  --name "${RUNNER_NAME}" \
  --labels "${RUNNER_LABELS}" \
  --unattended \
  --replace

2.4 Using actions/create-github-app-token in Runner Workflows

name: Register Runner with App Token
on:
  workflow_dispatch:
    inputs:
      runner_name:
        description: 'Runner name'

jobs:

          REG_TOKEN=$(curl -s -X POST \

      - name: Configure runner (on remote host via SSH)
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.RUNNER_HOST }}
          username: ${{ secrets.RUNNER_USER }}
          key: ${{ secrets.RUNNER_SSH_KEY }}
          script: |
            cd /opt/actions-runner
            ./config.sh \
              --url https://github.com/${{ github.repository }} \
              --token ${{ steps.reg-token.outputs.REG_TOKEN }} \
              --name ${{ github.event.inputs.runner_name }} \
              --labels "self-hosted,linux,x64" \
              --unattended --replace

3. PAT Rotation Runbook Best Practices

3.1 Critical Finding: No PAT API Exists

GitHub does NOT support programmatic creation or deletion of Personal Access Tokens via any REST or GraphQL API. There is no POST /user/personal-access-tokens endpoint. This is confirmed in GitHub Community Discussion #148626 (January 2025, still current as of April 2026). Any workflow claiming to "rotate PATs" is either rotating GitHub App installation tokens (not PATs), or using a semi-automated approach where a human manually creates the new PAT.

3.2 Fine-Grained PATs vs Classic PATs

Repository scopingExplicitly scoped to specific reposALL repos the user can access
Org admin visibilityFull visibility + audit trailInvisible (unless SAML enforced)
Org approval policiesCan require approvalNo approval mechanism
Org admin revocationCan revoke access to their resourcesCannot revoke
Auto-revocationRevoked if user loses accessNOT revoked
Default expiration30 days (org-enforceable)No default (can be infinite)

3.3 GITHUB_TOKEN Internals

Under the hood: GITHUB_TOKEN is actually a GitHub App installation access token. When you enable GitHub Actions on a repo, GitHub auto-installs a hidden GitHub App. Each job gets a new installation token for this hidden app. It is NOT a PAT.
AspectGITHUB_TOKENPAT

Cross-repo accessNo (without separate App)Yes (all repos in scope)
Branch protection bypassNo (not a user)Yes (if user is admin)

3.5 Semi-Automated PAT Rotation (Reminder-Based)

Since PATs cannot be created via API, the best you can do is automate distribution after a human creates the new token:

name: PAT Rotation Reminder
on:
  schedule:
    - cron: '0 9 1 * *'  # 1st of every month

jobs:
  remind:
    runs-on: ubuntu-latest
    steps:
      - name: Check PAT expiry
        env:
          GH_TOKEN: ${{ secrets.PAT_ROTATION_CHECKER }}
        run: |
          # This will fail with 401 if PAT is expired
          if gh api user 2>/dev/null; then
            echo "PAT still valid"
          else
            echo "::warning::PAT may be expired or invalid. Create a new one."
          fi

      - name: Notify
        if: failure()
        uses: slackapi/slack-github-action@v1.26.0
        with:
          payload: |
            {"text":"PAT rotation due! Create new PAT and update repo secrets."}

4. SLSA Provenance with GitHub Apps

4.1 How actions/attest-build-provenance Works

1. Subject Resolution  →  Resolve artifact (file path, container image, checksums file)
2. OIDC Token Acquisition  →  Request GitHub OIDC token (id-token: write)
3. Sigstore Certificate  →  Present OIDC token to Fulcio CA
   ├── Public repos  →  fulcio.sigstore.dev
   └── Private repos  →  GitHub private Fulcio instance
   Returns: X.509 cert (10-min TTL) binding OIDC identity to ephemeral keypair
4. Provenance Predicate  →  Build SLSA v1 predicate (builder.id, buildType, materials)
5. DSSE Envelope  →  Wrap in-toto Statement in DSSE envelope
6. Signing  →  Sign with ephemeral private key
7. Transparency Log  →  Upload to Rekor (public or private)
8. GitHub Attestations API  →  Persist attestation to repo

4.2 SLSA Level Achieved

LevelNameKey RequirementGitHub Actions?
L0NoneNo requirementsTrivially
L1DocumentedProvenance exists showing build platformYes
L2HostedDedicated infra + digitally signed provenanceYes
L3HardenedIsolated builds + non-falsifiable provenanceYes (hosted runners only)
L3 achieved on GitHub-hosted runners because: (1) VM-level isolation between runs, (2) signing keys managed by platform infrastructure not build steps, (3) builder.id is platform-controlled. On self-hosted runners, maximum L2 (no platform isolation guarantee).

4.3 Workflow Example — OIDC Keyless Signing

name: Build and Attest
on:
  push:
    branches: [main]

permissions:
  id-token: write       # Required for OIDC token
  attestations: write    # Required for GitHub Attestations API
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build
        run: |
          go build -o dist/myapp ./cmd/myapp
          sha256sum dist/myapp > dist/checksums.txt

      - name: Attest build provenance
        uses: actions/attest-build-provenance@v2
        with:
          subject-checksums: dist/checksums.txt

      # For container images:
      - name: Attest container image
        uses: actions/attest-build-provenance@v2
        with:
          subject-name: ghcr.io/${{ github.repository }}/myapp
          subject-digest: ${{ steps.build.outputs.digest }}

4.4 Verification

# Via gh CLI
gh attestation verify dist/myapp --repo owner/repo

# Via cosign (keyless)
cosign verify-attestation \
  --type slsaprovenance \
  --certificate-identity-regexp 'https://github.com/owner/repo/.github/workflows/.+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/owner/repo/myapp:latest

4.5 GitHub App Key Signing (for Self-Hosted Runners)

Self-hosted runners may not support OIDC. Use the GitHub App private key directly with cosign:

# One-time setup: import App key into cosign format
cosign import-key-pair --key github-app.private-key.pem
# Outputs: import-cosign.key (encrypted) + import-cosign.pub
# Store import-cosign.key as COSIGN_PRIVATE_KEY secret
# Distribute import-cosign.pub to verifiers

# In workflow:
- name: Sign with App key
  env:
    COSIGN_PASSWORD: ${{ secrets.COSIGN_PASSWORD }}
  run: |
    echo "${{ secrets.COSIGN_PRIVATE_KEY }}" > /tmp/cosign.key
    chmod 600 /tmp/cosign.key
    cosign sign-blob \
      --key /tmp/cosign.key \
      --output-signature dist/myapp.sig \
      dist/myapp
    rm -f /tmp/cosign.key

# Verify:
cosign verify-blob \
  --key cosign.pub \
  --signature dist/myapp.sig \
  dist/myapp

7. Migration Path: PAT → App Token

7.4 Step 3 — Update Git Remote (Critical)

# BEFORE: Embedded PAT in remote URL (SECURITY ISSUE)
git remote set-url origin https://x-access-token:${GH_PAT}@github.com/owner/repo.git

# AFTER: Use App token (or better, use GH_TOKEN env var)
# Option A: Still use token in URL but with App token
git remote set-url origin \
  https://x-access-token:${{ steps.app-token.outputs.token }}@github.com/owner/repo.git

# Option B (recommended): Use GH_TOKEN env var, no URL embedding
git remote set-url origin https://github.com/owner/repo.git
# Git credential helper will use GH_TOKEN automatically
# Or: git -c http.extraHeader="Authorization: Bearer $TOKEN" push
PMOVES finding: The embedded PAT in git remote URL was the root cause of branch protection bypass. The embedded token has push access but does not enforce branch protection rules. Switching to App token in the remote URL fixes the bypass AND enables proper branch protection enforcement.

8. PMOVES.AI Migration Assessment

Current State (as of 2026-04-23):
  • GH_PAT expired (HTTP 401 for API calls) but git push still works via embedded token in remote URL
  • Branch protection rules configured but bypassed — commits pushed directly to main
  • GH_APP_CLIENT_ID and GH_APP_SEC exist in repo secrets
  • MISSING: GH_APP_ID and GH_APP_INSTALLATION_ID — cannot generate App tokens without these
  • Runner fleet: 5 self-hosted runners (AI Lab, SPARK, cloudstartup, kvm4, kvm2) registered with PAT
  • Catch-22: PAT needed to call App installation endpoint, but PAT is expired

8.1 Resolution Path

Phase 0 — Break the Catch-22 (manual, one-time)
  1. Log into github.com/settings/tokens as the repo owner
  2. Create a new fine-grained PAT scoped to PMOVES.AI only
  3. Set expiry to 7 days (minimal window)
 4. Permissions: contents:read, administration:read (minimum for next step)
  5. Update GH_PAT env var on runners with new token

Phase 1 — Bootstrap App Authentication
  1. Use the fresh PAT to discover Installation ID:
     curl -H "Authorization: Bearer $NEW_PAT" \
       https://api.github.com/app/installations
  2. Add APP_INSTALLATION_ID to repo variables:
     gh variable set APP_INSTALLATION_ID --body "654321"
  3. Verify App token generation works:
     python3 -c "
       import jwt, time, requests
       # ... generate JWT, get installation token, test API call
     "

Phase 2 — Migrate Workflows
  1. Find all PAT references: grep -r 'secrets.GH_PAT' .github/
  2. Replace with actions/create-github-app-token pattern
  3. Fix git remote URLs on all 5 runners (remove embedded PAT)
  4. Test each workflow

Phase 3 — Migrate Runner Registration
  1. Update runner registration scripts to use App token flow
  2. Re-register each runner (AI Lab, SPARK, cloudstartup, kvm4, kvm2)
  3. Verify runners pick up jobs

Phase 4 — Harden
  1. Enable "Do not allow bypassing" on branch protection
  2. Delete GH_PAT secret from repo
  3. Delete GH_PAT env var from all runners
  4. Set up SLSA provenance (actions/attest-build-provenance)
  5. Consider ARC for scale-set runners (Phase 2 roadmap)

8.3 Cost Impact

Zero additional cost. GitHub Apps are free to create and use. Installation access tokens have a higher API rate limit (15,000/hr for org apps vs 5,000/hr for PATs). The migration eliminates the operational cost of PAT rotation and reduces security incident risk.
