# Credentials & Secrets Workflow

**Purpose**: How credentials are generated, stored, and injected across the PMOVES.AI stack.

---

## Key Principle: JWT Comes from Supabase

`JWT_SECRET` is **not a standalone credential** — it's the HMAC-SHA256 key that signs
Supabase ANON_KEY and SERVICE_ROLE_KEY tokens. All services that validate JWTs
(Agent Zero, Archon, Hi-RAG, a2ui-renderer) use `SUPABASE_JWT_SECRET`, which is a
legacy alias: `SUPABASE_JWT_SECRET = ${JWT_SECRET}`.

**Flow**: `generate-keys.sh` → JWT_SECRET → signs ANON_KEY + SERVICE_ROLE_KEY → all auth

## Credential Sources

### 1. CHIT Bundle (Local Secret Store)

The CHIT bundle is the **primary source for external API keys** on self-hosted runners.

| Property | Value |
|----------|-------|
| Location | `~/.config/pmoves/chit/env.cgp.json` |
| Format | JSON with hex-encoded secret values (no cleartext) |
| Permissions | `600` (owner-only read/write) |
| Generated by | `sync-secrets-local.yml` GitHub Actions workflow |
| Decoded by | `pmoves.chit.codec.decode_secret_map()` → plaintext dict |
| Consumer | `make secrets-funnel-sync` → `tools/secrets_sync.py generate` |

**Contains 19 API keys:**
- LLM providers: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `GROQ_API_KEY`,
  `MISTRAL_API_KEY`, `DEEPSEEK_API_KEY`, `XAI_API_KEY`, `VENICE_API_KEY`
- Aggregators: `OPENROUTER_API_KEY`, `TOGETHER_AI_API_KEY`, `FIREWORKS_AI_API_KEY`,
  `PERPLEXITYAI_API_KEY`, `COHERE_API_KEY`
- Embeddings: `VOYAGE_API_KEY`
- Infrastructure: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`
- Voice: `ELEVENLABS_API_KEY`
- Other: `Z_AI_API_KEY`, `GOOGLE_API_KEY`

**Decode flow:**
```
env.cgp.json → secrets_sync.py generate → env.shared (+ env.tier-*)
```

### 2. GitHub App (`GH_APP_ID` + `GH_APP_SEC` + `GH_APP_CLIENT_ID`)

Installed **org-wide** on all POWERFULMOVES repositories. Used in CI for GHCR auth
and available for runtime token minting by services (BoTZ MCP gateway, Archon).

| Property | Value |
|----------|-------|
| Purpose | Ephemeral tokens for GHCR, cross-repo ops, MCP GitHub tools |
| Action | `actions/create-github-app-token@v2` |
| Workflows | `build-images.yml`, `integrations-ghcr.yml`, `self-hosted-builds.yml` |
| Local setup | `docs/GITHUB_APP_LOCAL_SETUP.md` |
| Strategy doc | `pmoves/docs/infrastructure/github-app-strategy.md` |
| Secrets | `GH_APP_ID`, `GH_APP_SEC` (PEM), `GH_APP_CLIENT_ID`, `GH_APP_INSTALLATION_ID` |

**Token hierarchy:**
- **CI:** `actions/create-github-app-token@v2` → ephemeral `GITHUB_TOKEN` for GHCR
- **Runtime:** Services mint installation tokens from `GH_APP_ID` + `GH_APP_SEC`
- **MCP:** BoTZ GitHub MCP server uses minted tokens for org-wide GitHub API access

**NOT for pulling secrets** — GitHub API is write-only for secret values.

### 3. `sync-secrets-local.yml` Workflow

The bridge between GitHub Secrets (cloud) and the CHIT bundle (local machine).

| Property | Value |
|----------|-------|
| Trigger | `workflow_dispatch` (manual: GitHub UI or `gh workflow run`) |
| Runner | `[self-hosted, ai-lab]` (this machine = `POWERFULMOVES`) |
| Output formats | `cgp` (CHIT-encoded, default) or `env` (plaintext) |
| Output location | `~/.config/pmoves/chit/env.cgp.json` (cgp) or `~/.config/pmoves/secrets/local.env` (env) |

**When to run:** After rotating API keys in GitHub Secrets, or on first-time setup.

```bash
# Refresh CHIT bundle from GitHub Secrets
gh workflow run sync-secrets-local.yml --repo POWERFULMOVES/PMOVES.AI -f output_format=cgp
```

### 4. Local Generation Scripts

| Script | Purpose | When to Use |
|--------|---------|-------------|
| `pmoves/scripts/supabase/generate-keys.sh` | Generates JWT_SECRET, DB_PASSWORD, signs ANON/SERVICE_ROLE tokens | First-time setup or key rotation |
| `pmoves/tools/brand_defaults.py` | Applies seeded branded defaults (MinIO, Neo4j, Meilisearch, Invidious) | Every `make env-setup` run |
| `pmoves/scripts/bootstrap_env.py` | Interactive bootstrapper using `bootstrap/registry.json` | First-time setup with prompts |
| `pmoves/tools/credential_setup.py` | 6-step CLI wizard for multi-tier credential config | Manual per-tier setup |
| `pmoves/tools/push-gh-secrets.sh` | Push env values into GitHub Actions secrets | Syncing secrets to CI |

### What `brand_defaults.py` Auto-Generates

- **NEO4J_PASSWORD**: `pm_` + `secrets.token_urlsafe(16)` (if missing/empty)
- **MEILI_MASTER_KEY**: Strengthened to 32+ char token if < 16 chars
- **INVIDIOUS_COMPANION_KEY**: Exactly 16 chars (required by upstream)
- **INVIDIOUS_HMAC_KEY**: Strengthened to 32+ chars if weak
- Preserves all existing non-empty values (never overwrites set credentials)
- Mirrors `NEO4J_AUTH` to `.env.generated` for compose-only consumers

### What `generate-keys.sh` Produces

```
JWT_SECRET      → 64-char base64 random (openssl rand)
DB_PASSWORD     → 48-char base64 random
ANON_KEY        → JWT signed with role=anon using JWT_SECRET
SERVICE_ROLE_KEY → JWT signed with role=service_role using JWT_SECRET
```

## Credential Source Priority

```
1. CHIT bundle (~/.config/pmoves/chit/env.cgp.json)  ← decoded by secrets-funnel-sync
2. env.shared (pmoves/env.shared)                     ← gitignored, single source of truth
3. env.tier-* (auto-populated from env.shared)         ← per-tier subsets
4. .env.local (machine-local overrides)                ← gitignored
5. GitHub Secrets (CI-only, push via push-gh-secrets.sh)
6. CHIT manifest (pmoves/chit/secrets_manifest.yaml)   ← canonical variable definitions
7. bootstrap/registry.json                             ← declarative generation rules
```

**Data flow:**
```
GitHub Secrets ──[sync-secrets-local.yml]──→ CHIT bundle
                                                │
generate-keys.sh ──→ JWT_SECRET, DB_PASSWORD    │
brand_defaults.py ──→ Neo4j, Meili, Invidious   │
                          │                     │
                          ▼                     ▼
                       env.shared ◄── secrets-funnel-sync
                          │
                  populate-tier-envs
                          │
                    ┌─────┼─────┐
                    ▼     ▼     ▼
               env.tier-data  env.tier-llm  env.tier-agent ...
```

## Bootstrap Sequence

### Full Bootstrap (First-Time Setup)

```bash
# 0. (If API keys stale) Re-run sync workflow to refresh CHIT bundle
gh workflow run sync-secrets-local.yml --repo POWERFULMOVES/PMOVES.AI -f output_format=cgp

# 1. Generate Supabase keys (if first-time)
bash pmoves/scripts/supabase/generate-keys.sh
# Copy JWT_SECRET and DB_PASSWORD into pmoves/env.shared

# 2. Apply branded defaults + bootstrap env
make -C pmoves env-setup

# 3. Decode CHIT bundle + distribute to tier files
make -C pmoves secrets-funnel

# 4. Validate
make -C pmoves env-check
make -C pmoves auth-alignment
```

### Quick Refresh (After API Key Rotation)

```bash
# 1. Sync new keys from GitHub Secrets to CHIT bundle
gh workflow run sync-secrets-local.yml --repo POWERFULMOVES/PMOVES.AI -f output_format=cgp

# 2. Decode and distribute
make -C pmoves secrets-funnel-sync
make -C pmoves populate-tier-envs

# 3. Validate
make -C pmoves auth-alignment
```

### Guided Flow

```bash
make -C pmoves first-run    # Runs: env-setup → Supabase → core services → agents → demo data
```

## Make Targets Reference

| Target | Purpose |
|--------|---------|
| `env-setup` | Unified bootstrap: brand defaults + registry-driven env population + drift checks |
| `secrets-funnel` | Full pipeline: runtime hydrate → URL-encode → CHIT decode → audit gates |
| `secrets-funnel-sync` | CHIT manifest sync + decode bundle → materialize env files |
| `secrets-runtime-hydrate` | Pull runtime labels (Supabase/container status) into env.shared |
| `chit-export` | Encode env.shared values into CHIT bundle (reverse of decode) |
| `chit-manifest-sync` | Sync secrets manifest between source and destination |
| `bootstrap-tier-envs` | Create missing `env.tier-*` files from `.example` templates |
| `populate-tier-envs` | Populate tier env files with defaults from env.shared and .env.local |
| `check-tier-envs` | Validate all tier environment files exist |
| `env-check` | Cross-platform environment preflight checks |
| `auth-alignment` | Cross-tier credential consistency check (JWT, NATS, MinIO, URL-safety) |
| `first-run` | Guided first-run: env-setup, Supabase, core, agents, demo data |

### `secrets-funnel` Internals

The `secrets-funnel` target orchestrates these steps in order:
1. `secrets-runtime-hydrate` — pull Supabase/container labels into env.shared
2. `credential_urlencoder.py` — URL-encode special characters in credentials
3. `secrets-funnel-sync` — decode CHIT bundle → write to env.shared + tier files
4. `secrets-audit` — verify all required secrets are present
5. `tooling-audit` — verify tool availability
6. *(optional)* boot user target if `SECRETS_FUNNEL_BOOT_USER_TARGET` is set

## GitHub Secrets Sync

### Push: Local → GitHub

```bash
# Push from env.shared → GitHub Secrets (filtered by CHIT manifest allowlist)
./pmoves/tools/push-gh-secrets.sh --repo POWERFULMOVES/PMOVES.AI --env Dev

# With GHCR bootstrap
./pmoves/tools/push-gh-secrets.sh --repo POWERFULMOVES/PMOVES.AI --env Dev --ghcr-bootstrap
```

The manifest allowlist (`chit/secrets_manifest.yaml`) controls which variables are
eligible for push — prevents accidental exposure of local-only credentials.

### Pull: GitHub → Local

```bash
# Via self-hosted runner workflow (preferred)
gh workflow run sync-secrets-local.yml --repo POWERFULMOVES/PMOVES.AI -f output_format=cgp

# Manual decode if bundle already exists
make -C pmoves secrets-funnel-sync
```

## Placeholder Detection

Current `env.shared` placeholders that indicate incomplete bootstrap:

| Pattern | Meaning |
|---------|---------|
| `PLACEHOLDER_*_HERE` | Needs `generate-keys.sh` output |
| `YOUR_*_HERE` | Needs real external API key or CHIT bundle decode |
| `changeme` | Needs `brand_defaults.py` to strengthen |
| `NEO4J_PASSWORD_HERE` | Needs `brand_defaults.py` (auto-generates) |

## Post-Rotation Procedure

After rotating any credential:
1. Update source (GitHub Secrets for API keys, `generate-keys.sh` for JWT)
2. If API keys: `gh workflow run sync-secrets-local.yml` → wait → `make secrets-funnel-sync`
3. If local keys: Update `pmoves/env.shared` directly
4. Run `make -C pmoves env-setup && make -C pmoves env-check`
5. Run `make -C pmoves auth-alignment` to verify cross-tier consistency
6. Restart affected services via `make -C pmoves up-<profile>`

See `pmoves/docs/operations/SEEDED_BRANDED_DEFAULTS.md` for full credential catalog.
