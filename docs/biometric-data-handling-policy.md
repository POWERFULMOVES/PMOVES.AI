# PMOVES.AI Biometric Data Handling Policy

**Version**: 1.0.0
**Effective**: 2026-04-25
**Classification**: Internal — Security (Restricted)
**Authority**: PMOVES.AI Cyber Defence Initiative
**Legal Context**: Surveillance Accountability Act §2(b) — biometric data explicitly covered under warrant requirement

---

## 1. Purpose

This policy governs the collection, processing, storage, and deletion of biometric data within PMOVES.AI's media pipeline. It exists because:

- The Surveillance Accountability Act (Massie, 2026) explicitly extends warrant protection to biometric data including **facial images, face prints, gait, voice recognition, and other unique physical identifiers**
- PMOVES.AI services process voice, facial detection, and voice characteristic data as part of AI inference
- Biometric data is **irreversibly identifying** — unlike passwords, you cannot change your voice or face
- Even if PMOVES.AI is not the target of surveillance, **third-party services in our stack could be compelled or purchased** to expose biometric data we processed

> **Zero-Tolerance Principle**: Biometric data is the highest-risk data class. No biometric data persists beyond 24 hours. No exceptions. No exemptions. Not even for security incidents.

## 2. Biometric Data Definition for PMOVES.AI

### 2.1 In Scope (T4 Classification)

| Data Type | Generated By | Why It's Biometric |
-----------|-------------|-------------------|
 | **Voice prints** — speaker embedding vectors that can identify *who* is speaking | `ffmpeg-whisper` (:8078) via speaker diarization or speaker verification models | Uniquely identifies a person by vocal characteristics. Even without explicit speaker ID, embedding vectors can be matched across recordings. |
 | **Facial detection metadata** — bounding boxes, landmark coordinates, face embeddings | `media-video` (:8079) via YOLOv8-face or similar face detection models | Spatial coordinates of facial features can reconstruct face geometry. Embedding vectors are directly comparable across images. |
 | **Voice characteristic vectors** — pitch, formant, timbre feature arrays | `media-audio` (:8082) via emotion/voice analysis models | Composite voice features are near-unique per individual when combined. |
 | **Emotion profiles linked to voice** — emotion labels with voice-derived features | `media-audio` (:8082) | When paired with voice characteristics, creates a biometric-emotion profile that is personally identifying. |

### 2.2 Out of Scope (Lower Classification)

| Data Type | Why It's NOT Biometric | Classification |
-----------|----------------------|---------------|
 | Speech-to-text transcripts (what was said, not who said it) | Content-based, not identity-based — same as reading a document | T3 (7 days) |
 | Generic object detection ("person detected" without facial features) | Does not identify *which* person | T3 (7 days) |
 | Audio waveform / raw PCM (without feature extraction) | Raw signal without derived identifying features — but **escalate to T4 if speaker diarization is run on it** | T3 normally, T4 if diarized |
 | Video frames without face detection | Pixel data without biometric extraction | T3 (7 days) |

### 2.3 Gray Area Decision Matrix

| Scenario | Classification | Decision Rule |
-----------|---------------|---------------|
 | Whisper transcription with `--diarize` flag | **T4** | Diarization produces speaker segments = voice prints |
 | Whisper transcription without diarization | T3 | Text output only — no speaker identification |
 | YOLOv8 detecting "person" class (no face model) | T3 | Generic person detection, not biometric |
 | YOLOv8-face detecting face bounding boxes | **T4** | Face spatial data is biometric-enabling |
 | Emotion detection on text transcript | T3 | Emotion from content, not from voice characteristics |
 | Emotion detection from audio features | **T4** | Voice-derived emotion is biometric-adjacent |
 | Speaker embedding stored in vector DB | **T4** | Direct biometric template |
 | Audio chunked into segments for processing | T3 | Intermediate artifact, not biometric — **unless used for speaker comparison** |

## 3. Service-Specific Controls

### 3.1 ffmpeg-whisper (:8078) — Voice Processing

| Control | Requirement | Implementation |
---------|-------------|----------------|
 | **Speaker diarization** | **DISABLED by default** in production config. Enable only when explicitly requested and acknowledged. | Config flag: `WHISPER_DIARIZE=false` (env). When true, all outputs escalate to T4. |
 | **Speaker embedding extraction** | **NEVER extract or store speaker embedding vectors** in production. | Audit codebase for `speechbrain`, `resemblyzer`, `x-vectors` imports. Remove or gate behind dev-only flag. |
 | **Input audio files** | Delete immediately after transcription completes. Do not write to persistent storage. | Process from tmpfs mount only. Verify no copies in `/tmp`, `/app/data`, MinIO. |
 | **Transcript output** | T3 (7 days). Strip any speaker labels before persistence. | Post-processing step: remove `<speaker_1>`, `<speaker_2>` tags if diarization was accidentally enabled. |
 | **GPU memory** | Audio tensors in GPU VRAM are volatile — no action needed. | N/A |

### 3.2 media-video (:8079) — Video/Face Processing

| Control | Requirement | Implementation |
---------|-------------|----------------|
 | **Face detection model** | **DISABLED by default** in production. Use generic person/object detection only. | Config flag: `VIDEO_FACE_DETECT=false` (env). YOLOv8 `person` class is T3. YOLOv8-face is T4. |
 | **Face bounding boxes** | If face detection is enabled, bounding box coordinates are **T4 — 24 hour max**. Never persist to DB. | Write to tmpfs only. No MinIO upload. No database insert. |
 | **Face embeddings** | **NEVER extract or store face embedding vectors**. | Audit for `arcface`, `facenet`, `dlib` face recognition imports. Remove or dev-gate. |
 | **Input video files** | Delete immediately after frame extraction completes. | Process from tmpfs. Verify no copies persist. |
 | **Frame images with faces** | If face detection enabled, extracted frames containing faces are **T4 — 24 hour max**. Blur faces before any T3 persistence. | Post-process: apply Gaussian blur to detected face regions before saving to MinIO (T3 path). |
 | **Detection metadata (non-face)** | Object/person counts, labels — T3 (7 days). | Standard persistence path. |

### 3.3 media-audio (:8082) — Emotion/Voice Analysis

| Control | Requirement | Implementation |
---------|-------------|----------------|
 | **Voice characteristic extraction** | **DISABLED by default**. Emotion-from-text is T3. Emotion-from-voice-features is T4. | Config flag: `AUDIO_EMOTION_MODE=text_only` (default) vs `voice_features` (T4 escalation). |
 | **Voice feature vectors** | If voice-based emotion enabled, feature vectors are **T4 — 24 hour max**. Never persist. | Write to tmpfs only. No vector DB insertion. No MinIO upload. |
 | **Emotion labels from voice** | Paired with voice features = T4. Standalone text labels (without feature vectors) = T3. | Store only the emotion label string if decoupled from voice features. If coupled, T4 applies to both. |
 | **Input audio** | Delete immediately after analysis. | Tmpfs-only processing. |

### 3.4 Downstream Consumers

| Consumer | Risk | Control |
-----------|------|--------|
 | cipher-api (:8105) / Qdrant | Biometric vectors indexed for search | **NEVER index T4 data into Qdrant**. Gate at ingestion: reject payloads with biometric metadata tags. |
 | cipher-api (:8105) / Neo4j | Biometric data as graph node properties | **NEVER store T4 data as node properties**. Graph queries must filter out biometric-classified entries. |
 | Agent Zero (:5081) memory | Biometric data in agent context/memory | Agent Zero must never persist biometric data in FAISS memory or knowledge files. Tool call results containing biometric data must be marked volatile. |
 | MinIO (:9000) | Object storage of media artifacts | Bucket lifecycle policy: T4 objects auto-delete at 24h. Separate bucket `pmoves-biometric-tmp` with aggressive lifecycle. |
 | Hostinger (website deployment) | Accidental inclusion in deployed content | **Absolute ban**: no biometric data ever sent to Hostinger API. Audit deployment scripts. |
 | Telegram/Discord messaging | Biometric data in notification payloads | **Absolute ban**: no biometric data ever sent to messaging APIs. Notifications must be metadata-only (service name, status, generic description). |

## 4. Storage Architecture for T4 Data

### 4.1 The T4 Sandbox

All T4 biometric data, when it must exist temporarily during processing, is confined to:

```
Container tmpfs mount: /tmp/pmoves-bio/   (size: 500M, noexec, nodev, nosuid)
├── whisper/           # Voice prints, diarization segments
├── video-faces/       # Face bounding boxes, face frames
└── audio-voice/       # Voice characteristic vectors, emotion-from-voice features
```

**Properties**:
- **tmpfs** — exists only in RAM, never written to disk
- **Container-scoped** — destroyed when container restarts
- **No backup** — excluded from any volume mounts, MinIO replication, or snapshot policies
- **No network egress** — firewall rule: no outbound connections from processes writing to `/tmp/pmoves-bio/`
- **Automated purge** — cron every hour deletes anything older than 24 hours (defense-in-depth)

### 4.2 What NEVER Goes Anywhere

| Never store in... | Because... |
|-------------------|------------|
 | PostgreSQL / Supabase | Persists to disk, replicated, subject to backup — warrantable |
 | Qdrant vector DB | Indexed and searchable — biometric matching becomes trivial |
 | Neo4j graph DB | Queryable relationships — biometric linkage across sessions |
 | MinIO object storage | Even with lifecycle policy, exists on disk temporarily — minimizes but doesn't eliminate risk |
 | FAISS / Agent Zero memory | Persistent vector index — biometric search across all sessions |
 | ClickHouse / TensorZero metrics | Metadata about biometric processing could reveal who was processed |
 | Log files (stdout/stderr) | Biometric data in logs persists via log rotation — **must be redacted** |

### 4.3 Log Redaction

All three media pipeline services MUST redact biometric data from logs:

```python
# Required log filter for media pipeline services
import re

BIOMETRIC_PATTERNS = [
    (r'face_embedding:\s*\[.*?\]', '[REDACTED: face_embedding]'),
    (r'speaker_embedding:\s*\[.*?\]', '[REDACTED: speaker_embedding]'),
    (r'voice_features:\s*\[.*?\]', '[REDACTED: voice_features]'),
    (r'face_bbox:\s*\[.*?\]', '[REDACTED: face_bbox]'),
    (r'landmarks:\s*\[.*?\]', '[REDACTED: landmarks]'),
]

def redact_biometric_log(msg):
    for pattern, replacement in BIOMETRIC_PATTERNS:
        msg = re.sub(pattern, replacement, msg, flags=re.DOTALL)
    return msg
```

## 5. Processing Boundaries

### 5.1 The Biometric Processing Decision Tree

```
INPUT: Audio or Video file
│
├─ Is speaker diarization enabled?
│  ├─ YES → All outputs are T4 → tmpfs only, 24h max
│  └─ NO  → Continue
│
├─ Is face detection (not generic person) enabled?
│  ├─ YES → Face outputs are T4 → tmpfs only, 24h max
│  │        Non-face outputs (object labels) → T3 → 7d
│  └─ NO  → Continue
│
├─ Is emotion detection using voice features (not text)?
│  ├─ YES → Voice features + emotion labels are T4 → tmpfs only, 24h max
│  └─ NO  → Continue
│
└─ All remaining outputs → T3 → 7d max retention
```

### 5.2 Configuration Flags (Environment Variables)

| Flag | Default | Effect when `true` | T4 Escalation |
------|---------|-------------------|---------------|
 | `WHISPER_DIARIZE` | `false` | Enables speaker diarization | ✅ Yes — all outputs T4 |
 | `VIDEO_FACE_DETECT` | `false` | Enables face detection (vs generic person) | ✅ Yes — face data T4 |
 | `VIDEO_FACE_BLUR` | `true` | Blurs faces in frames before T3 storage | Mitigation (not escalation) |
 | `AUDIO_EMOTION_MODE` | `text_only` | `voice_features` enables voice-based emotion | ✅ Yes — voice features T4 |
 | `BIOMETRIC_LOG_REDACT` | `true` | Redacts biometric vectors from logs | Mitigation |
 | `BIOMETRIC_STRICT_MODE` | `true` | Rejects any T4 data from entering persistent stores | Enforcement |

## 6. Deletion Procedures (T4 Specific)

### 6.1 Automated (Primary)

```bash
# Runs every hour on host or init container
/opt/pmoves/scripts/delete-biometric-data.sh --max-age=24h --sandbox=/tmp/pmoves-bio/

# What it does:
# 1. Finds all files in tmpfs sandbox older than 24 hours
# 2. Securely overwrites with random bytes before deletion (shmfs — defense-in-depth)
# 3. Logs deletion to /var/log/pmoves/data-deletion-audit.log
# 4. Alerts if any T4 data found outside sandbox (misconfiguration detection)
```

### 6.2 Misconfiguration Detection

The deletion script also scans for T4 data where it **shouldn't** be:

```bash
# Alert conditions (not deletion — investigation required):
# - Biometric vectors in Qdrant collections
# - Face/voice metadata in PostgreSQL tables
# - Biometric-tagged objects in MinIO older than 1 hour
# - Biometric embeddings in FAISS indices
# - Unredacted biometric patterns in log files

# Each alert triggers:
# 1. Log to audit trail
# 2. Notify security channel (Discord/Telegram — metadata only, no biometric data in notification)
# 3. Block further processing until investigated
```

### 6.3 Emergency Biometric Purge

```bash
# Nuclear option — destroys ALL temporary biometric data immediately
/opt/pmoves/scripts/emergency-biometric-purge.sh --confirm --audit-log

# Also triggers:
# - Restart all media pipeline containers (flushes tmpfs)
# - Scan and alert on any persistent store contamination
# - Generate incident report template
```

## 8. Relationship to Surveillance Accountability Act

| Bill Provision | PMOVES.AI Response |
----------------|-------------------|
 | §1 — Warrant required for third-party data access | We minimize data at third parties (Supabase hosted tier). T4 data never reaches third parties. |
 | §2(b) — Biometric data explicitly covered (face prints, voice recognition, gait) | This entire policy. T4 classification maps directly to §2(b) protected data types. |
 | §2(b) — Includes data from robot vacuums, TVs, cameras in public | PMOVES doesn't collect this data, but our media pipeline could process it if uploaded. Same controls apply regardless of source. |
 | §3 — Private right of action | If PMOVES were compelled to produce biometric data, our deletion controls ensure there is nothing to produce after 24 hours. |

## 9. Exemptions

**None.**

Biometric data has zero exemptions. Not for security incidents. Not for legal holds. Not for model training. Not for debugging. If you need to retain biometric data beyond 24 hours, you are violating this policy — escalate to CTO for a policy amendment, not an exemption.
