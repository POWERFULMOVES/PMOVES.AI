# READ THIS BEFORE ADDING A LINE

# The Dockerfile installs upstream's requirements.txt FIRST (Stage 1), then this
# file SECOND, constrained by requirements.lock. Anything listed here is
# therefore installed *over* whatever upstream already resolved.
#
# So this file must contain ONLY what PMOVES code imports and upstream does not
# provide. Re-listing an upstream dependency here does not "make sure we get it"
# — it makes us the authority on its version, silently, forever.
#
# That is not hypothetical. This file previously carried 56 packages, of which
# 42 were verbatim copies of upstream's list that no PMOVES code imports, plus
# `playwright` and `browser-use`. Upstream v2.10 replaced playwright with
# patchright; our stale copy would have kept installing playwright==1.57.0 on
# top of it — a second browser stack, pinned by us, wanted by nobody.
#
# Rule: if `grep -r "import <pkg>"` finds nothing under this directory, it does
# not belong here. Version-pin only to fix a specific defect, and say which.

# --- NOT declared here on purpose ---
# anthropic, fastapi, prometheus-client, pydantic, uvicorn, flaredantic
# PMOVES code imports all of these, and it is tempting to list them. Do not.
#
# Stage 2 installs into the SAME venv it copied from stage 1 (/opt/venv-a0), so
# upstream's copies are already importable. Listing them here does not add them
# - it makes our lock the authority on the shared web stack, and our lock then
# installs *second*.
#
# That is not theoretical. fastapi caps starlette (fastapi<=0.124 requires
# starlette<0.51), so declaring fastapi here dragged starlette DOWN below the
# exact version upstream pins for a published advisory. The image ended up
# running a starlette the fork had deliberately moved off.
#
# All of them are declared where they belong: in the FORK's requirements.txt.
# There they participate in upstream's single coherent resolution - which picks
# fastapi 0.141.1 alongside upstream's pinned starlette - instead of fighting it
# afterwards. `anthropic` was moved there by PMOVES-Agent-Zero#18 for exactly
# this reason: it depends on pydantic, which the fork pins exactly, so resolving
# it here dragged pydantic to 2.13.4 and would have replaced that pin at runtime.
#
# Rule: if upstream and PMOVES both need a package, declare it in the FORK's
# requirements.txt, never here. This file is for things only PMOVES needs.
