# yt-dlp currency — what ships, how to check, and the gap

**Purpose.** This is the single place that answers "are we current on yt-dlp?".
Every number below is dated and paired with the command that produced it. If you
need today's answer, **run the commands** — do not trust the numbers, and do not
copy them into another doc. A pinned version number in prose is exactly what
produced the failure this document exists to correct (see § The #2713 record).

---

## 1. How to check (the mechanism — this does not rot)

yt-dlp is **not a pip dependency of PMOVES.AI**. It is the `PMOVES.YT` submodule,
which *is* a yt-dlp fork, and the deployed image installs that fork from its own
source tree. So "what version do we run?" has three different correct answers
depending on which layer you mean. Check all three; they drift apart.

### 1a. What the recorded gitlink carries — this is what ships to a fresh clone

```bash
# The recorded pin. Use ls-tree, NOT `git ls-files -s` (that reads the index and
# lies once anything is staged) and NOT the working checkout (it drifts on
# long-lived dev nodes).
git ls-tree HEAD -- PMOVES.YT

# The yt-dlp version at that exact pin.
git -C PMOVES.YT show <PIN_SHA>:yt_dlp/version.py | grep __version__
```

> **Caveat that bites.** `yt_dlp/version.py` is regenerated by upstream only at
> release time. A fork that has merged upstream `master` past a release still
> reports the *older* release string. The version number understates the code
> vintage. To date the code, find the newest upstream commit the pin contains:
> `git -C PMOVES.YT merge-base HEAD <latest-upstream-tag>`.

### 1b. What the running container reports — ask it, never infer

```bash
docker exec pmoves-pmoves-yt-1 python -c \
  "import yt_dlp; print(yt_dlp.version.__version__)"

# Or over the service's own health endpoint:
curl -s http://127.0.0.1:8077/healthz     # -> .yt_dlp.yt_dlp_version
```

### 1c. What upstream currently releases

```bash
# From a checkout that has the upstream remote:
git -C PMOVES.YT ls-remote --tags --refs https://github.com/yt-dlp/yt-dlp.git | tail -5

# Or, without git:
curl -fsSL https://pypi.org/pypi/yt-dlp/json | jq -r '.info.version'
```

### 1d. The size of the gap

```bash
git -C PMOVES.YT fetch upstream --tags
git -C PMOVES.YT rev-list --count HEAD..<latest-upstream-tag>   # commits behind
git -C PMOVES.YT rev-list --count <latest-upstream-tag>..HEAD   # commits ahead
git -C PMOVES.YT log --oneline --no-merges HEAD --not upstream/master  # the PMOVES commits
```

### 1e. The *other* yt-dlp in the fleet — do not forget this one

`channel-monitor` carries its own independent yt-dlp, pinned in
`pmoves/services/channel-monitor/requirements.lock`. It is a separate consumer
and no workflow touches it.

```bash
grep -A1 '^yt-dlp==' pmoves/services/channel-monitor/requirements.lock
```

### 2a. The pin is not on the tracked branch

`.gitmodules` declares `branch = PMOVES.AI-Edition-Hardened` for `PMOVES.YT`, but
the recorded gitlink `ebd39b7fc` is the tip of **`feat/upstream-sync-2026.07`**, an
unmerged feature branch. `PMOVES.AI-Edition-Hardened` is at `8d971cd18a`, three
commits behind the pin, and carries yt-dlp **2026.02.04**.

**Consequence:** `git submodule update --remote` follows the declared branch and
would **downgrade** the running yt-dlp from 2026.07.04 to 2026.02.04. Anyone
building from the fork's default branch gets the older extractor set. Merging
`feat/upstream-sync-2026.07` into `PMOVES.AI-Edition-Hardened` is a prerequisite
for the fork-sync lane, not part of it.

## 3. The #2713 record

PR #2713, `chore(pmoves-yt): bump yt-dlp to 2026.8.19` (`47c0c0d3b`), was
**docs-only**: `1 file changed, 1 insertion(+)`, a single line appended to
`docs/hardening/PMOVES-hardening-tracker.md`. The commit subject reads as a
version bump. Nothing was bumped.

This was not carelessness — it is what `.github/workflows/yt-dlp-bump.yml` is
built to do:

1. Resolve the latest yt-dlp from the PyPI JSON API.
2. Build `pmoves/services/pmoves-yt` with `YTDLP_VERSION=<latest>` and
   **`push: false`** — the image is validated, then discarded.
3. Commit **one prose line** to the hardening tracker and open a PR.

The workflow never writes a version into any file that a build reads. It also
builds `pmoves/services/pmoves-yt/Dockerfile`, which the deployed stack does not
use (compose builds `../PMOVES.YT` with `pmoves_yt_service/Dockerfile`; the
former is listed in `pmoves/configs/dockerfiles/_known_orphans.yaml`). So the
weekly job green-lights a build path production never takes, against stock PyPI
yt-dlp rather than the fork.

The tracker line is preserved in place for provenance, annotated rather than
deleted. The workflow's emitted wording has been corrected so future runs say
what they actually did.

## 4. The gap, stated for the fork-sync lane

**Facts only. Nothing here is scheduled — the fork-sync needs its own claim and
operator go-ahead.**

Current: pin `ebd39b7fc` @ yt-dlp 2026.07.04 (code through 2026-07-23), running.
Target: upstream 2026.08.19 (or `upstream/master`, 12 further commits).
Between them: 32 upstream commits, under 18 PMOVES commits that must survive.

A sync would have to:

1. **Reconcile the branch topology first.** Merge `feat/upstream-sync-2026.07`
   into `PMOVES.AI-Edition-Hardened` so the tracked branch and the recorded pin
   stop disagreeing (§ 2a). Until that holds, `--remote` is a downgrade.
2. **Merge, not rebase or reset.** `git merge upstream/2026.08.19` into Hardened,
   preserving the 18 PMOVES commits. Expect conflicts concentrated in
   `yt_dlp/extractor/youtube/` — the fork's Phase-9C multi-client chain and the
   Data API metadata path both sit where upstream's `#17461` / `#17462` client
   changes land.
3. **Regenerate `yt_dlp/version.py`** via upstream's `devscripts/update-version.py`,
   or accept that the reported version keeps understating the code (§ 1a).
4. **Rebuild and re-verify the runtime**, not just the build: confirm
   `GET :8077/healthz` reports the new version, then exercise a real ingest —
   a version string proves packaging, not extraction.
5. **Promote the gitlink** in PMOVES.AI as a separate reviewable commit, and let
   `submodule-gitlink-gate` confirm the new pin is an ancestor-or-tip of the
   tracked branch rather than a sibling.
6. **Decide `channel-monitor` separately.** It is pinned at 2024.10.7 (§ 1e) and
   is not covered by any of the above. A prior trail entry (2026-08-26, SPARK-KIMI)
   reports that this version returns 0 entries from flat playlist extraction and
   logs "No new videos" — a failure that reads as health. That is its own lane.
7. **Fix or retire `yt-dlp-bump.yml`.** As built it cannot bump a fork-sourced
   dependency (§ 3). Either it opens a real fork-sync PR, or it should be renamed
   to what it is — an upstream-release notifier — so its output stops being
   mistaken for a bump.
