| 4 | **defense-in-depth** | Git-bash on Windows cannot resolve absolute Windows paths (`C:\Users\...`) -- it sees `C:Users...` (colons and backslashes stripped/escaped). `tempfile.TemporaryDirectory()` uses `C:\Users\<u>\AppData\Local\Temp\` -- the test then writes a `.sh` there, calls `bash -n <path>`, and gets "No such file or directory". | The fix: cd into a per-test scratch dir under the repo (relative path always works) and run `bash -n <name>`. `tempfile.TemporaryDirectory` and a cwd change don't mix on Windows -- the cleanup races with the cwd change. | Any test that calls bash (or other Unix tools) on Windows from Python. |
| 5 | **reasoning-gap** | Python f-strings cannot contain `#` in expressions (PEP-701 f-string parser treats `#` as the start of a comment inside `{...}`). My first awk-based single-quote escape put the awk script inside the f-string body and the `gsub(...)` line broke parsing. The fix: compute the awk program in Python OUTSIDE the f-string and substitute via `awk_invocation` variable. | Confirmed via `python -m py_compile pmoves/tools/pmoves_launcher_generator.py`: `SyntaxError: f-string expression part cannot include '#'`. | Any future f-string template that needs to embed a small DSL (awk, sed, jq). |
| 6 | **semantic-naming drift** | `cli_tools.yaml` and `agent_registry.yaml` use INCONSISTENT signatures: claude_4090 uses `4090-claude` (per-node signing identity), kilocode_glm uses `kilocode` (tool family). This is not a generator bug -- it is the registry's deliberate design (Claude signs per-node in CHIT; KiloCode signs as the tool family). The generator must handle BOTH styles. | `claude_4090.signature=4090-claude` binds to family `claude` via the `-<family>` suffix rule; `kilocode_glm.signature=kilocode` binds via `DEFAULT_SIGNATURE_ALIASES`. Two rules, two paths. | Any cross-registry consistency work on PMOVES agent identities. |
| 7 | **contract-correctness** | Per-node pin files (`<cli>-<node>.{sh,ps1,cmd}`) are NEW callers of the canonical launcher. They are emitted EVEN for hand-managed tools (claude, crush) because they do not duplicate the launcher -- they set `PMOVES_NODE_ID` and `exec` it. The install scripts for the hand-managed tools are NOT emitted (would overwrite SDK-fixed refuse-linked-worktree guards + PATH shim recipe). | Asymmetric surface: launcher trio = hand, install script = hand, pin files = generator. | Any future "registry-driven" effort that wants to extend an existing hand-written surface. |
| 8 | **defense-in-depth** | The bash env-loading block needs to handle three escape classes in one `<f-while-read>` loop: (a) literal `${...}` (pass through for shell expansion), (b) single quotes (escape via `'\''`), (c) shell metacharacters (`[[:space:]]`, `\n`). The first implementation used `${val#*'${'}` to detect (a) -- brittle in f-strings (3 nested escape rounds) and broke both Python and bash. Final: `grep -qE '[$]{{'` + awk octal `\047`. The `[$]` is deliberate -- f-string's `${{` produces `${`, and `[$]` is a regex character class containing `$`, which avoids the f-string escaping double-up. | Built after 5 diagnostic rounds of f-string backslash mismatches. ## Diagnostic rounds (5 in one session, all template-bugs)

The single-quote-escape block went through 5 rounds of "fix the template" before the awk-octal approach won:

| Round | Approach | Failure |
|-------|----------|---------|
| 1 | Copy the original Claude launcher escape `\'/\'\\\'\'}}` directly into the f-string template | Python f-string parser saw `{{` then `{` as an open substitution, then complained "unmatched ')'". |
| 2 | Switch from `${val#*'${'}` to `case "$val" in *'${'*) ...` | The pattern `*'${'*` in f-string source `*'$'{{'{'*` had an unescaped `{` that broke the f-string parser. |
| 3 | Switch to `printf '%s=%s\n'` (single quotes around the format string) | The `\n` in Python source `\n` is the Python escape for newline (1 char), not literal `\n` (2 chars). Bash got `printf '%s=%s<NEWLINE>'` and complained. |
| 4 | Escape `\n` as `\\n` in the Python source | Bash got valid `printf '%s=%s\n'` BUT the next line had a different unescaped single-quote escape (`"s/'/'\\\\''/g"`) that put `''` (two single quotes) inside the f-string, which Python's parser mis-parsed. |
| 5 | Replace the inline bash single-quote escape with an awk program using `\047` (octal), built in Python OUTSIDE the f-string and substituted in as `{awk_invocation}` | Worked. Generator compiled, all emitted `.sh` files passed `bash -n`, all emitted `.ps1` files parsed. |

The root cause across all 5: trying to embed bash DSL fragments inside Python f-strings. The fix is structural: build the bash fragment in Python with explicit escape helpers (octal, ASCII codes), then substitute as a single variable. F-strings are great for trivial substitutions but should NEVER carry multi-layer escape sequences.

## What I'd do differently next time

1. **Build bash DSLs in Python first.** Any time the template needs to emit shell with multi-layer escape sequences (single quotes inside double quotes inside `case` patterns inside `printf`), build the bash fragment in Python using `chr(0x27)` / `\047` / `awk` and substitute as a single variable. F-strings should carry plain text + `{variable}` substitutions only.
2. **Test path encoding early.** Git-bash on Windows is not a Unix shell -- `C:\Users\...` becomes `C:Users...`. Build a helper `_bash_safe_path(p)` from the first commit, not after a 5-round diagnostic.
3. **Signatures first, names second.** The registry's `signature:` field is the contract, not `name:`. If I had started with the signature matcher and worked outward, the kilo alias bridge wouldn't have been a round of debugging.
4. **Hand-written surface isolation.** Any "let's regen X from registry" effort should explicitly enumerate what stays hand-written BEFORE writing the generator. PR #2847's FAIL-CLOSED roster is exactly the class of behaviour that gets lost when a "simple template" regenerates a hand-curated surface.

## SDK + doc provenance

- **Claude Agent SDK `--mcp-config <file>`** (https://docs.claude.com/en/api/agent-sdk/overview): the canonical mechanism for handing a curated MCP roster to a Claude session. The hand-written `claude-pmoves.sh:133-138` invokes `--mcp-config="$(jq -c '.mcpServers * { stdio: { env: env } }' "$MCP_INVENTORY")"` after FAIL-CLOSED roster normalization. The generator's template does NOT reproduce this FAIL-CLOSED gate -- it's load-bearing and belongs in the hand-written layer.
- **Wezterm `set-pane-environment-variables`** (https://wezfurlong.org/wezterm/config/lua/window/set_pane_environment_variables.html): the canonical pattern for binding env vars to a session surface. The per-node pin files (`claude-4090.cmd` etc.) are the PMOVES equivalent for a CLI surface: they set `PMOVES_NODE_ID=<node>` then exec the canonical launcher, so the registry is the canonical binding and parent env is overridden.
- **PowerShell `-NoProfile -ExecutionPolicy Bypass -File`** (https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe): the documented invocation pattern for a `.cmd` shim that runs a `.ps1`. Mirrored byte-for-byte in `claude-pmoves.cmd` and `crush-pmoves.cmd`; the generator's `.cmd` wrapper template uses the same one-liner.
