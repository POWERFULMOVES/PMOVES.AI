## P1 — the claim register cannot answer what is claimed

`pmoves/docs/AGENTS/AGNOTE4482PHI.t1.md`. Measured 2026-08-31:

```
CLAIM 154 · RELEASE 145

4090-CLAUDE   9 / 11        more RELEASEs than CLAIMs
5090-CLAUDE  14 / 17        "
Z890-CLAUDE  16 / 20        "
```

A lane cannot release more than it claims. The arithmetic inverts because one
node is counted under several names:

```
20 distinct agent names in the register
   1  exact match to agent_signatures.yaml      4090-claude
   6  match only if case is ignored             4090-CLAUDE, 5090-CLAUDE,
                                                B850-CLAUDE, Z890-CLAUDE,
                                                CLAUDE-OPUS, CRUSH
  13  not a signature at all                    Mavis, Mavis-5090, SPARK,
                                                SPARK-KIMI, KIMI-SPARK,
                                                SIDECAR-SPARK, CLAUDE-OPUS-5,
                                                CRUSH-GLM52, Z890, CODEX-GPT5,
                                                ANTIGRAVITY-OPUS,
                                                MISSING-LINK-HERMES,
                                                PMOVES-MINIMAX
```

The SPARK node appears under **four** names. `Mavis` / `Mavis-5090` are the
5090's lane. `4090-CLAUDE` / `4090-claude` are one machine.

This is `_HOST_MAP` keyed by `laptop`, one layer up: an identity binding with no
canonical form and no validator.

**Fix shape.** Normalising the history is the smaller half. The durable half is
a gate: every CLAIM/RELEASE must name an id that exists in
`agent_signatures.yaml`, case-sensitively. Personas that are real lanes
(`Mavis`, `SPARK-KIMI`) need signatures or an explicit alias table — inventing
either without the operator is how you get a 26th name.

**Do not** normalise silently. Several lanes will turn out to be genuinely open
once the spellings merge, and that is information.

## P1 — `role_class` is a schema, not a model

```
class             104/104 (100%)   standard 49 · specialized 29 · utility 25 · ci 1
type                0/104 (  0%)
role_class          2/104 (  1%)
resilience_class    0/104 (  0%)
```

`role_classes.worker` is defined as *"the only role_class that writes"* — the
sharpest statement in the taxonomy, and it is assigned to one agent. **Nothing
in the fleet can answer "is this agent allowed to write?" from the registry.**

Assigning write authority across 104 agents is a governance act, not a docs
edit. Suggested order: a gate requiring new agents to declare a `role_class`,
then backfill.

Two smaller registry defects alongside it:
- `class` carries an undeclared value `ci` (one agent); `legendary` is declared
  and unused.
- `worker` is a value in **both** `types` and `role_classes`, meaning
  implementation-kind and write-authority. Zero agents carry both today, so it
  is latent — exactly where `verify` was before it bit.

## FIXED — the sitrep skill reported a healthy NATS as DOWN

Six skills probed `localhost:8222`. The base compose publishes the monitor as
`${NATS_MONITORING_BIND:-127.0.0.1}:${NATS_MONITORING_PORT:-9223}:8222`
(`docker-compose.yml:3136`), so 8222 is the *container-side* port and, on a
default node, closed:

```
curl localhost:8222/healthz   ->  DOWN   (what the skills reported)
curl localhost:9223/healthz   ->  OK     uptime 2d15h, 7 connections
```

Also: the skills preferred `.claude/scripts/node-sitrep.sh`, **which did not
exist**, so they always took the inline fallback — which is why nobody noticed.

**The obvious fix would have been wrong.** `docker-compose.z890.yml:32`
publishes `127.0.0.1:8222:8222`. Replacing the literal `8222` with the literal
`9223` in all six copies would have fixed four nodes and broken the Z890. And
`NATS_MONITORING_BIND` moves the *host* half too, so keeping only the port —
which the first version of the fix did — reintroduces the same false DOWN on
any node not bound to loopback (Codex caught this).

Shipped in #2861: one derivation in `.claude/scripts/nats-endpoint.sh`, called
by everything, hardcoding neither half and reporting *measured* vs *assumed*.
The `pmoves-z890.ts:8222` cross-machine probe is annotated as correct-and-not-
to-be-derived, since `docker port` reads the **local** daemon.

The generalisable lesson is not about ports: **a value measured on one node and
written down as a fleet law is a defect even when the measurement was right.**
Twice in this session — this, and `no header -> 200`, which Z890's hardened
container corrected to `401`.

## P2 — the announcer is never invoked

`pmoves/tools/agent_terminal_theme.py` has no caller: no make target, no
launcher, no bring-up path. `botz_cli.py:51` says *"full rendering delegates to
agent_terminal_theme"* — it now shares the host map (#2849) but still renders
its own output.

The wiring half was deliberately split from #2849. Intended shape, per the
operator: the announcer reports **alongside** service validation, not instead of
it — identity, roster source and server count, service health, in one themed
block at bring-up, so a node announces its state rather than passing silently.

## Operator decision — AutoClaw writes into `AGENTS.md`

An AutoClaw tool appends managed blocks to the repo's **Tier-1** doc — the file
every agent on every node reads first. A `<!-- autoclaw:zcode-app-context-v1 -->`
block appeared uncommitted on 2026-08-31 and blocked a `--ff-only`; a sibling
`autoclaw:feishu-lark-skill-guidance` block is already tracked.

It surfaced only because it blocked a fast-forward. `git add -A` would have
committed it silently — the same hazard as submodule gitlink rollbacks.

Two questions: should those blocks be committed or regenerated on demand, and
should a tool be writing into `AGENTS.md` at all.
